AI Voice Studio — Accessibility Guidelines

This document defines the accessibility standards that all code in AI Voice Studio must follow. The application is designed from the ground up to be fully usable with screen readers (NVDA, JAWS, Narrator) and keyboard-only navigation.

Core Principles

These principles are derived from WCAG 2.1 (Level AA), Microsoft Active Accessibility (MSAA), UI Automation (UIA), and the requirements of the NVDA, JAWS, and Narrator screen readers.

Rule 1: Every interactive control must have an accessible name. Screen readers announce controls by their accessible name. Without one, the control is silent or reads its raw class name.
Rule 2: Every control must have a visible label or an accessible description. Both sighted users and screen reader users must understand what each control does.
Rule 3: All functionality must be available via keyboard. No mouse-only interactions. Tab through controls, use Enter/Space to activate, Escape to cancel, arrow keys for lists and combos.
Rule 4: Focus must be visible and managed. The focused control must have a visible indicator. Focus must move logically through the UI. When a dialog opens, focus must land on the first interactive control.
Rule 5: Dynamic content changes must be announced. When content changes (progress, status, errors), screen readers must be notified via accessible name updates or live regions.

Accessible Names

On Windows, wxPython's SetName() sets the MSAA/UIA accessible name. This is what NVDA, JAWS, and Narrator announce.

Rules

  • Every wx.Button, wx.TextCtrl, wx.ComboBox, wx.CheckBox, wx.RadioButton, wx.ListBox, wx.ListCtrl, wx.Gauge, and wx.StaticText that conveys information must have SetName() called.
  • The accessible name should be concise but descriptive.
  • Avoid redundant names like "button" in button names — screen readers already announce the role.
BAD: btn.SetName("Button1") — meaningless
GOOD: btn.SetName("Start recording") — clear purpose
BAD: combo.SetName("Combo") — redundant role
GOOD: combo.SetName("Select TTS engine") — describes purpose

Tooltips

Every control that might need explanation should have a tooltip via SetToolTip(). Tooltips provide extra context for sighted users and are announced by some screen readers when the control is focused.

GOOD: btn.SetToolTip("Download the optional CUDA GPU runtime (~1.8 GB)")

Label Association

Labels (wx.StaticText) must be associated with their controls both visually (placed next to the control in the layout) and programmatically (via SetName() on the control matching the label text).

Using add_labeled()

The a11y.add_labeled() helper creates both the visual label and sets the accessible name in one call:

from ai_voice_studio.gui.a11y import add_labeled

add_labeled(parent, grid, "Select TTS", self.tts_combo,
            flag=wx.LEFT | wx.RIGHT, border=2)
# This creates:
#   - A StaticText with "Select TTS:" label
#   - Sets tts_combo.SetName("Select TTS")

Manual Labeling

For controls not using add_labeled(), always call SetName() with the same text as the visual label:

# The label text must match what the screen reader announces
self.btn = wx.Button(parent, label="Start recording")
self.btn.SetName("Start recording")
self.btn.SetToolTip("Begin synthesizing audio for all pending segments")

Keyboard Navigation

Tab Order

  • Controls must be added to sizers in logical tab order (top-to-bottom, left-to-right).
  • The first interactive control in a dialog should receive focus when the dialog opens.
  • Use wx.CallAfter(control.SetFocus) for post-construction focus.

Enter Key Handling

In the Settings dialog, Enter activates OK (NVDA convention). Inside multi-line text boxes, Enter inserts a new line instead. Inside buttons, combo boxes, and list boxes, Enter is passed through to the control.

Focus Management

  • When a modal dialog opens, focus must land on the first interactive control (or the category list in Settings).
  • When a wizard page changes, focus must move to the new page's first control.
  • After an action completes (download, recording), focus should return to a logical position.
  • Focus must never be lost — every screen must have at least one focusable control.

Screen Reader Announcements

When dynamic content changes, screen readers must be notified. In wxPython, the primary mechanism is updating the accessible name of a status control:

# When recording progress changes:
self.status.SetLabel("Recording segment 3 of 10")
self.status.SetName("Recording status: segment 3 of 10")
# Screen reader announces the updated name

# When log content loads:
self.log_text.SetName(f"Log file {filename}: showing last 200 of 1500 lines")
# Screen reader announces how many lines are shown

Patterns

  • Progress updates: Update both SetLabel() and SetName() on the status text.
  • Error messages: Use wx.MessageBox which is natively accessible, or update an accessible name.
  • Completion: Announce "Recording complete" or "Download finished" via accessible name.
  • Content loading: When loading logs, files, or lists, update the accessible name to describe what was loaded.

Color and Contrast

  • Text must have sufficient contrast against its background (WCAG AA: 4.5:1 for normal text, 3:1 for large text).
  • Never rely on color alone to convey information (e.g. red for error, green for success — also use text or icons).
  • The theme system must preserve contrast ratios in both Light and Dark modes.
  • Focus indicators must be visible in all themes.

Dialogs and Windows

  • Every dialog must have a descriptive title set in the constructor.
  • Use wx.DEFAULT_DIALOG_STYLE | wx.RESIZE_BORDER for resizable dialogs that work at different DPI settings.
  • Use CreateSeparatedButtonSizer(wx.OK | wx.CANCEL | wx.APPLY) for standard button layout — these are natively accessible.
  • Category panels in Settings use the NVDA SettingsPanel pattern with _SettingsPanelAccessible.

Menus and Shortcuts

  • All menu items must have mnemonics (the & character in labels).
  • Frequently used actions must have keyboard accelerators.
  • The menu bar must be navigable with Alt+letter keys.

Error Handling

  • All error messages must be presented in accessible dialogs (wx.MessageBox with wx.ICON_ERROR).
  • Error messages must be clear and actionable ("What went wrong" + "What to do about it").
  • Errors in background threads must be posted to the UI thread via wx.CallAfter() or wx.PostEvent().
  • When heavy logging is enabled, all caught exceptions are logged automatically via exc_info=True.
