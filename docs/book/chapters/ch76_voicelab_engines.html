Chapter 76

Voice Lab: Building a Voice-Cloning Engine Subsystem

Learning Objectives

  • Design a plugin registry that describes engines as data instead of code
  • Turn a pip-installed model package into a catalog-shaped voice entry
  • Drive a long-lived worker subprocess over a JSON-lines protocol
  • Plug one engine wrapper into an existing engine cache without touching call sites
  • Separate pure request-building code (easy to test) from the process code around it

76.1 Why a New Subsystem Was Needed

The first version of the Voice Clone page drove a single engine through one dedicated client class. Every new clone engine then promised the same four things — install me, list my voices, load my model once, speak text — but with completely different Python packages, different package names and different numbers of built-in voices. Writing one client per engine would have multiplied the same bugs by three.

The current design keeps the shape of the app (tts.engine.get_engine still returns something with a synthesize() method) and puts all the differences into data:

ConcernWhere it lives nowWhy
Which engines exist, what they install, which voices they shipvoicelab/engines.pyPure data — importable without PyTorch, no GUI, testable
Per-engine tuning knobs (steps, temperature, seed…)voicelab/options.pyOne shared vocabulary, validated in one place
Actually running an enginevoicelab/worker.py (standalone script)PyTorch must never be imported into the GUI process
Talking to the workervoicelab/__init__.py (CloneWorker)One IPC implementation for every engine
App-facing adapterVoicelabEngineImplements the existing TtsEngine.synthesize contract
The three engines in the current build are Pocket TTS (Kyutai, pocket-tts), Bark (Suno, via transformers) and F5-TTS (f5-tts). All three run on the CPU and can additionally run on an NVIDIA GPU — see Chapter 78. An earlier fourth engine (NeuTTS) was removed from the project: it required a Hugging Face login, which no part of this application should depend on.

76.2 Engines as Data: the Registry

Every engine is one dictionary. The fields are deliberately small in number, because each one has exactly one consumer:

{
    "id": "pocket_tts",
    "name": "Pocket TTS (Kyutai)",
    "engine": "pocket_tts",
    "package": "pocket-tts",
    "packages": ("pocket-tts", "soundfile", "scipy"),
    "license": "Apache-2.0 (code); per-voice licenses",
    "homepage": "https://github.com/kyutai-labs/pocket-tts",
    "size_hint": "~450 MB (model) + PyTorch",
    "devices": "cpu+gpu",
    "voice_cloning": True,
    "note": ( ... one paragraph shown in the UI ... ),
    "languages": _languages(("en", "fr", "de", "es", "it", "pt"),
                            "pocket_v1", "Pocket TTS 100M"),
}

Explain Line by Line Code Description (Block 1)

  1. Lines 1–3: id, name, engine
    id is the key used everywhere else (settings keys, voice entries, worker requests). name is only ever displayed. engine is the string the voice entry carries so that tts.engine.get_engine can find the right wrapper; keeping it equal to id is a convention, not a requirement.
  2. Line 4: "package": "pocket-tts"
    The single pip distribution whose presence means “this engine is installed”. Chapter 77 shows how this one string decides both “Install engine…” availability and which virtualenv the worker is started with.
  3. Line 5: "packages": (...)
    Everything handed to pip install. Plain names only — deliberately no version specifiers, because the same tuple is used by “Remove engine” and pip uninstall cannot accept requirements like name<1.0.
  4. Line 6: "license"
    Shown in the install dialog and matched by the licence table in the packaged THIRD-PARTY-LICENSES.html (Chapter 82). F5-TTS is the important case: the code is MIT while the weights are CC-BY-NC-4.0, which forbids commercial use.
  5. Lines 7–8: homepage, size_hint
    Documentation the user can act on before downloading gigabytes. size_hint is a string on purpose: it is an estimate for humans, not a number any code branches on.
  6. Line 9: "devices": "cpu+gpu"
    Read by gpu_supported() with the substring test "gpu" in devices. Every Voice Lab engine is cpu+gpu: the CPU always works, the GPU is an addition — never a replacement.
  7. Line 10: "voice_cloning": True
    Lets the UI show the “clone your own voice” affordance only for engines that can actually do it. A flag in data beats an isinstance check in the GUI.
  8. Lines 11–12: note
    A paragraph from the registry straight into a label — the user reads the engine’s own description instead of a paraphrase maintained in the GUI.
  9. Lines 13–14: languages
    Built by the helper _languages() in the same catalog shape the JSON model catalog uses (code → name → variants → voices), so panels that already render catalog data render Voice Lab engines with no new code.

76.3 Voices That Come From the Package

Sherpa-onnx engines download model artifacts and then expose voices from the downloaded files. Voice Lab engines are different: their voices are supplied by the installed Python package, so they cannot live in the JSON catalog. Bark alone would need 130 rows (twelve languages × ten speakers plus the lightweight English checkpoint), and F5-TTS points at reference files inside its own wheel.

The solution is a factory that produces entries in exactly the shape ModelStore.installed_voices returns:

def _entry(engine_id, language, variant, voice, voice_name, **extra):
    entry = {
        "tts": engine_id,
        "tts_name": engine_name(engine_id),
        "language": language,
        "variant": variant,
        "voice": voice,
        "voice_name": voice_name,
        "sid": 0,
        "engine": engine_id,
        "dir": "",
        "builtin_voice": True,
        "requires_package": probe_package(engine_id),
    }
    entry.update(extra)
    return entry

Explain Line by Line Code Description (Block 2)

  1. Line 1: the signature
    Positional arguments describe the voice; **extra carries engine-specific additions (Bark’s repo, F5-TTS’s ref_resource). A variadic tail keeps the factory generic while still allowing one engine to add fields.
  2. Lines 2–4: tts, tts_name, engine
    Three keys that mean almost the same thing, each consumed by a different layer: tts is what the Download panel groups by, tts_name is the label, engine is what get_engine switches on. Reconciliation happens once, here, instead of in five panels.
  3. Lines 5–8: language, variant, voice, voice_name
    The same four-part voice identity used by the JSON catalog, so a voice entry is interchangeable no matter where it came from.
  4. Line 9: "sid": 0
    Speaker id for engines that address voices numerically. PyTorch engines address voices by name (Bark’s v2/en_speaker_3), so the numeric id stays a harmless default rather than a special case in the renderer.
  5. Line 10: "dir": ""
    Empty on purpose: these voices have no model directory on disk. Panels that display dir get an empty string instead of a path that does not exist — the absence is stated, not implied.
  6. Line 11: "builtin_voice": True
    How the UI knows this voice cannot be downloaded or removed; it is a property of the engine’s package.
  7. Line 12: "requires_package"
    Usually the same field name the catalog uses for “this engine needs a pip package in the shared environment”. Reusing it means the existing installed/not-installed logic applies unchanged — the panel that greys out unavailable voices needs no Voice Lab branch.
  8. Lines 13–14: entry.update(extra)
    Applied last so an engine may override a default if it must, and so callers that pass nothing get exactly the generic entry.

The Bark generator is worth reading because it shows how much UI code a data factory removes:

if engine_id == "bark":
    voices = []
    for code, label in _BARK_LANGUAGES:
        for speaker in range(10):
            voices.append(_entry(
                "bark", code, "bark_v2", f"v2/{code}_speaker_{speaker}",
                f"{label} speaker {speaker + 1} (of 10)",
            ))
    for speaker in range(10):
        voices.append(_entry(
            "bark", "en", "bark_small", f"v2/en_speaker_{speaker}",
            f"Bark small - English speaker {speaker + 1} (of 10)",
            repo="suno/bark-small",
        ))
    return voices

Explain Line by Line Code Description (Block 3)

  1. Lines 2–3: the nested loops
    Twelve languages × ten speakers = 120 preset voices, generated instead of typed. When Bark adds a language, one tuple entry adds ten voices.
  2. Line 5: f"v2/{code}_speaker_{speaker}"
    Bark’s speaker id format. The v2/ prefix is part of the identifier Bark itself expects, so it is built here rather than patched in later.
  3. Line 6: the human label
    “English speaker 3 (of 10)” tells the user how many options exist, which changes how they listen. Generating labels from data keeps them consistent for all 120 voices.
  4. Lines 8–13: the small-checkpoint voices
    suno/bark-small is English-only but much lighter on a CPU, so it is offered as a separate variant of English with repo set on the entry. The worker later prioritises repo over the default checkpoint, which is how the variant choice reaches the model loader.
Voice lists like this are the reason count_builtin_voices() exists as a public helper: the GUI shows “26 voices”, and a test can assert that number without re-implementing the loop.

76.4 Driving an Engine in a Subprocess

PyTorch and friends are heavy, slow to import and occasionally crash the process. None of that belongs in a GUI process that also holds the user’s recordings. The application therefore runs voicelab/worker.py as a separate interpreter process and talks to it over pipes:

{"cmd": "ping"}
{"cmd": "synthesize", "engine": "bark", "device": "cuda", "text": "...",
 "threads": 15, "voice": "v2/en_speaker_3", "repo": "suno/bark",
 "options": {"temperature": 0.7}}

One line of request in, one line of JSON out. The worker keeps the model loaded between requests, so recording 200 segments pays the load cost once. CloneWorker._ensure_proc starts the process and immediately sends ping — a worker that cannot even import its engine answers with an error before the first paragraph of a book is involved.

class CloneWorker:
    def __init__(self, engine_id, device=DEVICE_CPU, timeout=1800.0):
        self.engine_id = engine_id
        self.device = resolve_device(device)
        self._proc = None
        self._lock = threading.RLock()
        self._timeout = timeout
        self._next_id = 0

Explain Line by Line Code Description (Block 4)

  1. Line 1: class CloneWorker
    One instance per (engine, device) pair. The class owns exactly one process; the module-level worker_for() cache gives callers a shared instance so two panels do not start two copies of a multi-gigabyte model.
  2. Lines 2–3: the constructor’s first statements
    resolve_device is called once, here: “auto” or “gpu” becomes a concrete cpu/cuda at construction time, so every later request describes what is actually happening rather than what the user asked for.
  3. Line 4: self._proc = None
    The process is created lazily on first use. Constructing a worker is free, which is what lets the GUI build voice lists — and tests create workers — without spawning interpreters.
  4. Line 5: self._lock = threading.RLock()
    A re-entrant lock, because the recording thread writes a request and then reads a response; RLock means a helper called from inside the locked section cannot deadlock itself. It is the only synchronisation the class needs, since a process pipe is otherwise usable from several threads.
  5. Line 6: self._timeout = 1800.0
    Thirty minutes. A CPU Bark run on a long paragraph is slow but healthy; a shorter timeout would kill work that is still progressing. A timeout exists at all so a wedged process cannot freeze the recording forever.
  6. Line 7: self._next_id = 0
    Request counter reserved for pairing requests with responses. JSON-lines is strictly sequential today; the id makes a future interleaved protocol possible without re-designing the class.

76.5 Building the Request (Pure Code, Easy Tests)

The hardest part of any IPC layer to test is the plumbing. The trick used here is to move every decision out of the plumbing: build_synthesize_request() takes plain values and returns a plain dictionary, so a unit test can assert the exact JSON the worker would receive with no process and no wx involved.

def build_synthesize_request(*, engine_id, device, text,
                             voice_entry=None, speed=1.0, tuning=None):
    entry = voice_entry or {}
    resolved = resolve_device(device)
    request = {
        "cmd": "synthesize",
        "engine": engine_id,
        "device": resolved,
        "text": text,
        "speed": float(speed),
        "threads": cpu_thread_count(),
    }
    for key in _VOICE_KEYS:
        value = entry.get(key)
        if value:
            request[key] = value
    if engine_id == "bark" and not request.get("repo"):
        request["repo"] = ("suno/bark-small"
                           if entry.get("variant") == "bark_small" else "suno/bark")
    overrides = _options.clean(engine_id, tuning)
    if not overrides:
        overrides = _options.clean(engine_id, entry.get("options"))
    if overrides:
        request["options"] = overrides
    return request

Explain Line by Line Code Description (Block 5)

  1. Lines 1–2: keyword-only parameters (*)
    The leading * forbids positional arguments. With six similar strings in play (“engine”, “device”, “text”), a positional call is a silent bug; keyword-only forces every call site to name what it passes.
  2. Line 3: entry = voice_entry or {}
    Still works when no voice entry is supplied (a quick preview may have none), and never mutates the caller’s dictionary.
  3. Line 4: resolved = resolve_device(device)
    “auto” is turned into a concrete device before the request is built, so the JSON on the wire is always truthful and the worker never needs to know what “auto” means.
  4. Lines 5–12: the base request
    Six keys every request carries. threads comes from cpu_thread_count(), which delegates to compute.cpu_threads() — the 80–95 % band of Chapter 78. The worker does not decide how much CPU to use; the application does, and the worker applies it.
  5. Lines 13–16: copying the voice keys
    Only non-empty values are copied, from an explicit allow-list (_VOICE_KEYS). An allow-list beats “send the whole entry” for two reasons: the request cannot leak UI-only fields into the engine, and the set of fields the worker must understand stays small enough to document.
  6. Lines 17–20: the Bark checkpoint rule
    Bark downloads one of two repositories. The variant (“Bark small”) is a voice-list concept the engine does not know, so it is translated here into the repository the worker passes to transformers. Note the not request.get("repo") guard: an entry that already set repo (as _entry does for bark-small voices) wins, so both paths agree.
  7. Lines 21–24: tuning overrides
    Two carriers are supported and cleaned by the same validator: the function argument (Settings defaults applied by the panel) and the voice entry (per-project overrides stored in the project). Empty results are omitted entirely, so an untouched project sends no options key at all and the engine uses its own defaults.

76.6 Plugging Into the Existing Engine Cache

The rest of the application knows only one thing about a speech engine: it can be asked to turn text into int16 samples. VoicelabEngine implements that contract and nothing more.

class VoicelabEngine:
    def __init__(self, voice_entry, device=DEVICE_CPU):
        engine_id = voice_entry.get("engine")
        if not engines.is_engine(engine_id):
            raise VoicelabError(f"'{engine_id}' is not a Voice Lab engine.")
        self.voice_entry = voice_entry
        self.engine_id = engine_id
        self.tuning = _options.clean(engine_id, voice_entry.get("options"))
        self.device = resolve_device(
            voice_entry.get("device") or device or DEVICE_CPU)
        self.sample_rate = _DEFAULT_SAMPLE_RATE
        self._worker = worker_for(engine_id, self.device)

    def synthesize(self, text, sid=0, speed=1.0, pitch=1.0, volume=1.0):
        if not text.strip():
            raise ValueError("Nothing to synthesize")
        request = build_synthesize_request(
            engine_id=self.engine_id, device=self.device, text=text,
            voice_entry=self.voice_entry, speed=speed, tuning=self.tuning)
        samples, sample_rate, report = self._worker.synthesize(request)
        self._report_unused_options(report)
        self._report_notes(report)
        if sample_rate:
            self.sample_rate = sample_rate
        if pitch != 1.0:
            samples = _shift_pitch(samples, pitch)
        if volume != 1.0:
            samples = _apply_volume(samples, volume)
        return samples

Explain Line by Line Code Description (Block 6)

  1. Lines 2–5: the guard clause
    A voice entry from the wrong source (say, a sherpa-onnx voice) fails immediately with a clear message instead of building a request no worker can serve. VoicelabError is a dedicated exception type so callers can catch engine problems without catching everything.
  2. Lines 8–9: self.tuning
    The voice entry’s stored overrides are validated once at construction. Validation is not repeated per segment, and a malformed value can never reach the worker.
  3. Lines 10–12: device resolution order
    The voice entry wins, then the constructor argument, then CPU. This ordering is what makes “this project records on the GPU” survive from the Recording window all the way to the process.
  4. Line 13: worker_for(...)
    Returns the shared worker for that (engine, device). Two engines, or the same engine on two devices, still get separate processes — a CUDA process cannot change its device mid-run.
  5. Lines 16–17: the empty-text guard
    A blank segment (a page containing only a heading marker, say) would otherwise cost a model run that produces silence. Failing fast keeps the synthesizer’s error handling in charge.
  6. Lines 18–20: the request
    All the intelligence lives in the pure builder — this method only decides which parameters come from the instance and which from the call.
  7. Lines 21–23: the response triple
    samples, the engine’s real sample_rate and a report dictionary. The report is not an error channel: it carries “these options were skipped” and human notes such as “audio was decoded with soundfile because this machine has no FFmpeg”.
  8. Lines 24–27: adapting the sample rate
    Each engine speaks at its own rate (24 kHz here). Updating self.sample_rate from the response means the writer downstream creates WAV files with the correct header even if an engine changes its rate between versions.
  9. Lines 28–32: pitch and volume
    Pitch shifting and volume are applied by the application, on the returned samples, using the same helpers as the ONNX engines. One implementation means the Audio Effects slider behaves identically no matter which engine spoke, and an engine that cannot do pitch shifting does not need a new parameter.
Keep heavy imports out of the GUI. Nothing in voicelab/__init__.py imports torch. Voice lists, device detection and request building all work with plain Python + NumPy — which is also why the whole subsystem is unit-testable on a machine with no GPU and no models.

76.7 Mini Project: A Voice List From a Registry

Build a tiny script that turns the registry into a report — the same shape of work the Settings pages do:

from ai_voice_studio.voicelab import engines

for engine_id in engines.engine_ids():
    info = engines.engine(engine_id)
    print(f"{info['name']:<34} {engines.count_builtin_voices(engine_id):>4} voices")
    print(f"    installs : {', '.join(engines.packages(engine_id))}")
    print(f"    license  : {info['license']}")
    print(f"    gpu      : {engines.gpu_supported(engine_id)}")

76.8 Key Takeaways

  • Describe engines as data; then the GUI, the installer and the worker all read one source of truth
  • Generate catalog-shaped voice entries so existing panels need no special cases
  • Never import a heavy ML framework into the GUI process — run it in a worker subprocess
  • Keep request building pure: no processes, no wx, completely unit-testable
  • An adapter that satisfies the existing interface is cheaper than teaching every call site about a new engine type
  • Send “how much of the machine to use” from the application, and let the worker apply it
