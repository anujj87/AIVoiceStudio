Chapter 91

Chunks, Windows and the Picture-Change Gate

Learning Objectives

  • Separate the unit that bounds memory from the unit that bounds a description
  • Plan windows that tile a chunk exactly and stay inside a cap
  • Handle a request written before windows existed
  • Tell the model what the previous description said, so it reports change
  • Skip a window whose picture has not moved — and never skip one on a guess

91.1 One Summary per Chunk Was Not Enough

Chunking exists for real reasons: a model call can only hold so many frames, a long film has to be stoppable, and progress has to be visible. But a chunk is a terrible unit for a description. A two-minute chunk at half a frame per second samples sixty frames; a 12 GB card can hold about four of them in one prompt, so the model was shown four stills spread over two minutes and asked for one or two sentences. On a real lecture that produced:

"A man in a black shirt sits in a chair, speaking into a microphone, while handwritten notes on a whiteboard to his left show evolving text including 'old data → (spam) (Non-spam)' and 'patterns ↓ use → (New)'."

That sentence is not wrong, and it is useless as audio description. It does not say what appeared, when it appeared, or what the man did — because four frames cannot answer those questions and one answer per two minutes does not try to. The same video described with a twenty-second unit produced ten descriptions, each naming what had just happened: the gesture, the line written on the board, the diagram that changed.

So the two duties were separated:

Twenty seconds is not arbitrary: it is the cadence broadcast audio description uses, and it is short enough that "what is happening now" and "what has changed" are the same question.

91.2 Planning the Windows

The windows of a chunk tile it exactly, with no gap and no overlap, and no window is longer than AD_MAX_WINDOW_SECONDS. That cap matters: the setting decides detail, and a user who leaves it at a very large value must not silently get one summary per chunk back.

def plan_windows(chunk, window_seconds=AD_WINDOW_SECONDS):
    start = _positive(chunk.get("start"))
    end = _positive(chunk.get("end"))
    if end <= start:
        return []
    size = _positive(window_seconds) or AD_WINDOW_SECONDS
    size = min(size, AD_MAX_WINDOW_SECONDS)
    size = max(1.0, size)
    windows = []
    index = 0
    cursor = start
    while cursor < end - 1e-9:
        stop = min(cursor + size, end)
        windows.append({"index": index, "start": round(cursor, 3),
                        "end": round(stop, 3), "duration": round(stop - cursor, 3),
                        "chunk": chunk.get("index")})
        index += 1
        cursor = stop
    return windows

engine.plan_for_video() attaches the windows of every chunk to the plan it returns, so the count the GUI shows and the windows the worker is handed come from one place:

chunks = pipeline.plan_chunks(duration, chunk_seconds)
for chunk in chunks:
    chunk["windows"] = pipeline.plan_windows(chunk, window_seconds)
return {"video": video_path, "duration": duration, "ffmpeg": ffmpeg_exe or "",
        "chunks": chunks, "windows": pipeline.window_count(chunks),
        "window_seconds": float(window_seconds)}
Backward compatible by construction. The worker describes each entry of windows when the request carries them, and treats a chunk as a single window when it does not: for window in (list(chunk.get("windows") or []) or [chunk]). A request from an older build therefore still describes the whole chunk, exactly as it used to.

91.3 Telling the Model What It Already Said

A model asked to describe a piece of video with no memory of the last description answers with the scene: "a man sits in a chair beside a whiteboard". A model asked the same question with the previous description in front of it, and asked by name for the change, answers with the difference — which is what a listener who has heard the last description actually needs.

def _window_instruction(request, previous=""):
    base = str(request.get("chunk_instruction")
               or "Describe this piece of video in one or two short sentences.")
    previous = str(previous or "").strip()
    if not previous:
        return base
    return (base
            + "\n\nThe previous description was: " + previous
            + "\nThese frames come straight after it. Say what is happening now "
            "and what has changed since that description - text, code or numbers "
            "that have appeared or changed, what the person does, anyone or "
            "anything new on screen. Do not repeat what was already described.")

The worker keeps the last description it produced and passes it with the next window. Only a description that was actually said counts — a window that was skipped, or that the model answered with "No significant visual change", leaves the previous text where it was.

91.4 The Picture-Change Gate

A window that shows exactly the picture the listener has already been told about is worth nothing: it repeats a description, and in extended audio description it also stops the film and spends eleven seconds saying the same thing again. The gate is a cheap, honest comparison of two frames.

Frames are compared as 64×36 grey summaries rather than pixel for pixel, because the only question is "does the picture move at all" and the small summary ignores H.264 and JPEG noise for almost nothing:

SIGNATURE_SIZE = (64, 36)
MIN_PICTURE_CHANGE = 2.0

# | What the chunk shows | Mean change |
# | a picture genuinely held | 0.00 - 0.07 |
# | a speaker shifting, no slide change | 1.15 - 1.47 |
# | a slide advanced or a cut | 3.12 - 7.53 |

Those numbers were measured on a real three-minute lecture and on synthesised stills, and they are the reason the threshold sits at 2.0: it is between "the scene is the same and someone moved" and "the picture is a different one". The gate compares every frame the window was sampled from, not only the ones that fit one prompt, so a brief change inside a window is not missed; and the reference is the last frame of the last window that was described, so a still picture held across a boundary is recognised as the picture the listener has already heard about.

A guess is never grounds for silence. picture_changed() answers True when it cannot judge: a single frame with no reference, no frames at all, a frame that cannot be read — and the very first window of a video, always, because the opening is what tells the listener what they are looking at. What a wrongly described window costs is time; what a wrongly skipped one costs is the only account the listener was going to get of something that did change.

91.5 The Worker's Loop

Put together, the worker's loop is a loop over windows that keeps two pieces of state across them:

described_reference = None   # the last frame the listener was told about
previous_text = ""           # the last description that was actually produced
total = sum(len(chunk.get("windows") or [chunk]) for chunk in chunks)
described = 0
for chunk in chunks:
    for window in (list(chunk.get("windows") or []) or [chunk]):
        described += 1
        frames = _extract_frames(ffmpeg, video, window["start"], window["end"],
                                 fps, scratch_dir, MAX_FRAMES_PER_CHUNK)
        signatures = frame_signatures(frames)
        repeat = described > 1 and not picture_changed(
            signatures, described_reference, min_change)
        if repeat:
            _emit(..., "the picture has not changed ... it is skipped.")
            continue
        described_reference = signatures[-1] if signatures else described_reference
        text = _describe_chunk(processor, model, torch, request, frames,
                               instruction=_window_instruction(request, previous_text))
        if text and text.strip().lower().rstrip(".") != NO_CHANGE:
            previous_text = text.strip()
            _emit_segment({"start": window["start"], "end": window["end"],
                           "text": text.strip(), "chunk": window["chunk"],
                           "window": window["index"]})

Each finished window is written to stdout as an AIVS-SEGMENT| line the moment it exists, which is what lets the job refresh the description script on disk after every piece: closing a long run never loses the pieces that were already described.

91.6 Exercises

  1. Make the window length follow the frame rate, so a coarser rate describes longer pieces. What has to change in the estimate?
  2. The gate is a mean absolute difference over the whole frame. Design a test that distinguishes "a line of text appeared on a white slide" from "the speaker leaned forward".
  3. Extend the worker's report so a skipped window says why it was skipped (nothing changed, versus no room to speak it).

Key Takeaways

  • The unit a run is cut into and the unit a description covers are different questions, and answering both with one number costs the feature its usefulness.
  • Plan windows in the pure module, and hand the worker exactly what it must describe.
  • Tell the model what it already said, and ask for the change by name; a model with no memory describes the scene.
  • Skip a repeat only when a measurement says so, and always describe what you cannot judge.
