Chapter 87

The Theme Studio: Making Appearance a User-Editable Data Model

Learning Objectives

  • Model a look as a small palette plus a paint style, instead of dozens of hard-coded colours
  • Lay a user-created theme beside the built-in ones without a special case anywhere
  • Generate a stable, unique id from a name so two themes called “Dark” cannot collide
  • Give a live preview on every change without re-applying the theme to the whole application
  • Keep a wallpaper a per-theme record that survives editing and deletion
  • Do the whole thing on the GUI thread, in a dialog that a screen reader can drive

87.1 A Theme Is Six Colours and a Style

Chapter 35 built theming around a palette. The current implementation turns that palette into a declarative object, so a theme is data rather than a branch in a paint routine:

class ThemePreset:
    """A predefined theme: a name, a palette and a signature wallpaper style."""

    __slots__ = ("theme_id", "name", "colors", "pattern", "note")

The palette has exactly six keys, and every window in the application is painted from them:

KeyPaints
bgwindow and panel backgrounds
fgordinary text
control_bgbuttons, text boxes, list backgrounds
control_fgtext on those controls
accentthe painted pattern and highlights
headingheadings and emphasised labels

Six is not an arbitrary number. It is the smallest set that keeps a dark theme readable and consistent — a control needs its own background and foreground or it inherits the window's and disappears — while staying small enough that a person can choose all of it from a form. Anything larger would be a colour picker with thirty entries and no way to keep them coherent.

The style is chosen from a fixed list of painters:

PATTERNS: Tuple[Tuple[str, str], ...] = (
    ("solid", "Solid colour"),
    ("gradient_v", "Vertical gradient"),
    ("gradient_h", "Horizontal gradient"),
    ("diagonal", "Diagonal gradient"),
    ("vignette", "Soft vignette"),
    ("grid", "Grid"),
    ("dots", "Dots"),
    ("stripes", "Stripes"),
    ("rays", "Corner glow"),
    ("waves", "Waves"),
)

Each id maps to a small drawing function (_draw_grid, _draw_waves…) that takes the device context, the size and the palette. Adding a style is adding one function and one row to this tuple — nothing else in the program changes.

87.2 Ten Predefined Themes, Built by One Helper

The predefined themes are declared with a constructor that keeps the six baseline keys in a fixed order, so a missing key is a visible bug rather than a silent fallback to black:

def _preset(theme_id, name, bg, fg, control_bg, control_fg,
            accent, heading, pattern, note) -> ThemePreset:
    """Build a preset palette, keeping the four baseline keys first."""
    return ThemePreset(
        theme_id, name,
        {"bg": bg, "fg": fg, "control_bg": control_bg,
         "control_fg": control_fg, "accent": accent, "heading": heading},
        pattern, note,
    )

THEME_PRESETS: Tuple[ThemePreset, ...] = (
    _preset("graphite_midnight", "Midnight Graphite",
            "#16181c", "#e6e9ef", "#22262d", "#e6e9ef", "#8ab4f8", "#ffffff",
            "gradient_v", ...),
    _preset("obsidian_gold", "Obsidian Gold", ...),
    ...                                        # ten in all
)

Every preset carries its own signature style, which is why ten dark themes do not feel like one theme in ten tints: Obsidian Gold uses a different pattern and a different accent from Forest Pine, and the painted look differs as much as the colours do.

87.3 User Themes Live in the Same List

A custom theme is a dictionary in the settings file. The important decision is that the rest of the application never knows the difference: it asks for the palette of a theme id, and resolve_palette() answers from one source or the other.

"custom_themes": [ { "id": "custom:ocean-noon", "name": "Ocean Noon",
                      "bg": "#0b1c2c", "fg": "#e8f1f8", ... , "pattern": "waves",
                      "note": "" } ]

The id is generated, not typed by the user, and mangling a name into a slug means a person may safely create, delete and re-create themes with the same name:

def new_theme_id(settings, name: str) -> str:
    """A unique ``custom:`` id derived from ``name``."""
    slug = re.sub(r"[^a-z0-9]+", "-", (name or "theme").strip().lower()).strip("-")
    slug = slug or "theme"
    existing = {r.get("id") for r in custom_themes(settings)}
    candidate = CUSTOM_PREFIX + slug
    counter = 2
    while candidate in existing:
        candidate = f"{CUSTOM_PREFIX}{slug}-{counter}"
        counter += 1
    return candidate

Saving replaces by id and appends, so an edit and a new theme are the same operation:

def save_custom_theme(settings, record: Dict) -> str:
    """Store ``record`` (adding or replacing it); return its id."""
    theme_id = record.get("id") or new_theme_id(settings, record.get("name", ""))
    record = dict(record)
    record["id"] = theme_id
    records = [r for r in custom_themes(settings) if r.get("id") != theme_id]
    records.append(record)
    settings.set("custom_themes", records)
    settings.save()
    return theme_id
Deleting a theme deletes its wallpaper with it. A wallpaper is stored per theme id, so a deleted theme's record would be orphaned data that grows forever and could be resurrected by a later theme that happens to reuse the slug. delete_custom_theme() removes both in one step — the same "clean up the side table" discipline Chapter 82 applied to licences.

87.4 The Studio Is a Form with a Live Preview

Settings → General → Create custom theme… opens gui/theme_studio.py. Its structure is deliberately plain: a name box, six colour pickers, a pattern choice, optional wallpaper controls and a preview panel. Every picker's change handler repaints the preview only:

class ThemeStudioDialog(wx.Dialog):
    """Custom theme creator (Settings -> General -> Create custom theme...)."""
    _COLOUR_FIELDS = (("bg_picker", "bg", "Background"), ...)

Repainting the whole application on every colour change would be slow and, on a screen reader, disruptive. Repainting one panel is instant and gives the user the feedback they actually asked for. The theme is applied to the application only when the dialog is accepted.

The preview also shows the pattern: because the pattern painters are the same functions the welcome screen uses (paint_background()), the preview cannot disagree with the real thing. That is a recurring theme of this book: make the preview and the product the same code path, and the preview stops being a promise.

87.5 Wallpapers: the Welcome Screen's Own Record

The welcome screen is a full-width action bar of the four main buttons above a left projects sidebar. The large area that remains is the only surface a wallpaper may paint — it never paints behind a button or the project list, because a busy background behind text is an accessibility problem, not a style choice.

A wallpaper is stored per theme, with three fields:

"wallpapers": {
    "graphite_midnight": {"enabled": true, "image": "C:\\pics\\dunes.jpg", "pattern": ""},
    "custom:ocean-noon":  {"enabled": true, "image": "", "pattern": "waves"},
}
  • enabled — shows or hides it without forgetting the choice;
  • image — the user's own picture, aspect-filled; when the file cannot be loaded the painter falls back to the pattern instead of leaving a blank panel;
  • pattern — an override of the theme's signature style, or empty to use the theme's own.
def set_wallpaper(settings, theme, *, enabled=None, image=None, pattern=None):
    """Update the wallpaper record for ``theme`` and persist it."""
    record = dict(get_wallpaper(settings, theme))
    ...
    record["pattern"] = pattern if pattern in PATTERN_IDS else ""
    wallpapers = dict(settings.get("wallpapers", {}) or {})
    wallpapers[theme] = record
    settings.set("wallpapers", wallpapers)
    settings.save()

Note the validation: an unknown pattern id is stored as empty rather than saved and later ignored. Settings files are edited by hand, and a value that cannot be honoured should not be kept around to confuse the next reader.

87.6 Applying It, and Undoing It

apply_theme(top, theme, settings) resolves the palette and paints top and every descendant, and main.py calls it at startup and after the Settings dialog closes. Because the current theme id is in the settings file, the look survives a restart; because the palette resolves from one function, the System default, the two built-ins, the ten presets and any number of user themes all take exactly the same path through the code.

Contrast is a test, not a taste. A theme whose background and text are too close makes the application unusable with a screen reader or with low vision. The theme tests check each palette's contrast and each pattern's legibility, so a new preset cannot ship unreadable — the same "turn a convention into a failing test" rule the book has used since Chapter 17.

87.7 Exercises

  1. Add a "high contrast" pattern that ignores the accent and draws only bg and fg. Which contrast rule does it have to satisfy?
  2. Add theme export and import as a JSON file. What has to happen to the wallpaper's image path when the file moves to another machine?
  3. Make the studio offer "duplicate this theme" from the theme list. Which existing function does that, and what does it need to change?

Key Takeaways

  • Model appearance as data: six colours, a named style and a note, not scattered literals.
  • Let user themes into the same resolution path as the built-ins; a special case is a bug waiting to happen.
  • Generate ids from names, with a counter for collisions, so names stay human and ids stay unique.
  • Repaint a preview, apply on accept — and make the preview call the same painters as the real screen.
  • Keep a wallpaper a per-theme record, validated on write and removed with its theme.
