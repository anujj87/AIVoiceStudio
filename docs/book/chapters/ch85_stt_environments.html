Chapter 85

One Python Environment per Model: Isolation as a Product Decision

Learning Objectives

  • Decide when isolation is worth gigabytes, and prove the decision with a dependency conflict
  • Probe an environment by reading site-packages on disk instead of running pip
  • Split an install plan into a CUDA step and a plain-PyPI step
  • Drive a one-shot worker subprocess through request and response files
  • Turn a noisy stderr into the one line that is the actual cause of a failure
  • Explain a failure to the user in the words of the thing that failed

85.1 The Conflict That Forced the Design

Speech-recognition models look interchangeable from the dialog. Underneath, they are not: they are four completely different stacks whose transitive pins collide on every shared dependency.

Model familyNeedsConflicts with
Whisper (faster-whisper)CTranslate2, NumPyIts CUDA runtime is a wheel, not a pip dependency
Qwen3-ASR, Voxtral, Granite, Moonshinetransformers + a specific PyTorchEach other, whenever their PyTorch pins differ
NeMo (Canary-Qwen, Parakeet)nemo_toolkit, protobuf, its own PyTorchtransformers 5 — NeMo 3.0 crashes on it
SpeechBrainspeechbrain, torchaudioAnything that pins torchaudio elsewhere

Two of these cannot even be built on the same protobuf. Sharing one site-packages directory between them would mean installing a new model could silently break a model that used to work — the worst kind of bug, because nothing in the new install looks wrong. So the project repeats the decision it already made for the Voice Lab engines: one environment per model, under a sibling of the engine environments:

%APPDATA%\AIVoiceStudio\
├── tts_envs\<engine>        # the Voice Lab engines
├── stt_envs\<model id>     # one speech-recognition model each
├── addon_env               # addons and the Developer tab
└── settings.json
Never the same folder as the TTS side. The two trees are deliberately separate. A model's environment is named after its catalog id (stt_envs\qwen3_asr), so an engine and a model can never be handed each other's site-packages by a naming collision.

85.2 The Install Plan

Installing is a small pipeline, and the order matters. On Windows the PyPI torch wheel is CPU-only, so a GPU machine must fetch PyTorch from the CUDA index first, before the rest of the requirements are resolved against it:

#: Packages that must come from the CUDA PyTorch wheel index on a GPU machine
#: (PyPI's plain ``torch`` wheel is CPU-only on Windows).
_CUDA_PACKAGES = {"torch", "torchaudio", "torchvision"}

The plan a model produces is therefore a list of pip steps, each with its own index: on a GPU machine the CUDA PyTorch packages go first from the PyTorch wheel index, and everything else — the rest of pip_packages plus the catalog's cuda_packages — follows in one PyPI step. On a CPU machine there is a single PyPI step and cuda_packages is simply never added, so a CPU user never downloads a runtime they cannot load. After pip finishes, the environment is asked to import the back-end once; a dependency combination that cannot load is reported in the install dialog rather than appearing later as a crash on the first transcription.

def install_plan(model_id: str) -> List[Tuple[List[str], Optional[str]]]:
    """The pip steps that install a model into its own environment."""
    packages = list(catalog.pip_packages(model_id))
    steps: List[Tuple[List[str], Optional[str]]] = []
    if _has_cuda():
        cuda = [p for p in packages if base_name(p) in _CUDA_PACKAGES]
        if cuda:
            steps.append((cuda, PYTORCH_CUDA_INDEX))
            packages = [p for p in packages if base_name(p) not in _CUDA_PACKAGES]
        packages.extend(catalog.cuda_packages(model_id))
    if packages:
        steps.append((packages, None))     # None means the ordinary PyPI index
    return steps
Verification belongs at install time. A model can install "successfully" and still fail to import — a compiled extension built for a different Python, or a version pin that pip resolved in a way the author did not intend. Importing once, in the environment's own interpreter, turns that into one clear sentence at the moment the user is paying attention.

85.3 Probing Without a Subprocess

The Settings page shows what is installed. The obvious implementation — run pip list in the environment — would freeze the GUI on every repaint and shell out dozens of times. Instead the probe reads site-packages directly from disk: distribution metadata lives in a predictable place, so the installed versions are a directory read, cached and invalidated by the folder's timestamp.

#: name -> (timestamp, {normalized distribution name: version})
_DISK_CACHE: Dict[str, Tuple[float, Dict[str, str]]] = {}
_LOCK = threading.RLock()

The lock is there because the Settings page and a background install can both ask at once. The cache makes the check free after the first call; the timestamp makes it correct after an install, without a manual "refresh".

85.4 Running the Model in Its Own Interpreter

The application never imports a model's back-end. It writes a request file, starts the worker as a one-shot subprocess on the environment's own python.exe, and reads the answer back from a JSON file:

def _run_worker(model_id: str, request: Dict[str, Any], on_progress) -> List[Dict[str, Any]]:
    """Start the worker in the model's environment and read its JSON response."""
    script = environments.worker_script()
    python_exe = environments.runtime(model_id).python_exe
    ...
    tmpdir = tempfile.mkdtemp(prefix="aivs_stt_")
    request_path = os.path.join(tmpdir, "request.json")
    out_path = os.path.join(tmpdir, "response.json")
    request = dict(request)
    request["out"] = out_path
    with open(request_path, "w", encoding="utf-8") as fh:
        json.dump(request, fh, ensure_ascii=False)

    result = subprocess.run(
        [python_exe, script, request_path],
        capture_output=True, text=True, creationflags=flags,
    )
    ...
    with open(out_path, "r", encoding="utf-8") as fh:
        response = json.load(fh)
    return list(response.get("segments", []))

Three details are load-bearing:

  1. The answer comes from a file, not stdout. A model prints progress bars, download notices, NeMo's info logs and PyTorch warnings to the same stream. Parsing stdout would mean parsing all of that. A file the worker writes at the end is unambiguous, and stdout stays available as the diagnostic channel.
  2. One request per process. Loading a large model takes seconds to minutes; if the process stayed alive between files, the application would have to manage its lifetime, its memory and its cancellation. A one-shot process gets all three from the operating system, and the job's Cancel simply stops starting new ones.
  3. CREATE_NO_WINDOW on Windows. Without it a black console window flashes for every transcription.

The request itself carries only what the catalog and the dialog decided:

request: Dict[str, Any] = {
    "audio": audio_path,          # the file to transcribe
    "backend": backend,           # faster_whisper / transformers / nemo / ...
    "variant": variant,           # the checkpoint the user chose
    "language": language,         # "auto" or an ISO code
    "translate_to": translate_to, # "" or a target language
    "accuracy": accuracy,         # fast / balanced / best -> a beam size
    "compute": _resolve_device(compute),   # "cpu" or "cuda"
    "model": model_id,
    "runner": catalog.runner_for(model_id, variant),  # pipeline / chat / ...
    "timestamps": catalog.supports_timestamps(model_id),
    "trust_remote_code": catalog.needs_remote_code(model_id),
}

85.5 Errors People Can Act On

When the worker fails, the only evidence is its stderr, and most of that stderr is not the reason. A model download prints a progress bar to the same stream a crash uses, so the last line of a killed worker is often a finished download rather than an exception.

#: Fragments that mark a line as a progress bar rather than a cause.
_PROGRESS_MARKERS = ("%|", "it/s", "s/it", "B/s")

#: Lines a back-end prints that are never the reason a run failed.
_WARNING_MARKERS = (
    "deprecated", "futurewarning", "userwarning", "deprecationwarning",
    "warnings.warn", "[transformers]",
)

#: Log prefixes whose lines are routine chatter.
_LOG_PREFIXES = ("[nemo ", "[torch", "w1002", "w1003", "a100")

Lines matching those patterns are dropped, and the remaining meaningful line becomes the message. Two final touches make the result honest:

  • when the process exited non-zero, the exit code is appended ("(the model's process exited with code -1073741819)") — a Windows access violation and a Python exception need different fixes, and the code is how you tell them apart;
  • when the model was never installed, the error is a BackendMissing that names the environment and the command rather than a bare traceback.
raise BackendMissing(
    f"{entry['name']} has no Python environment of its own yet "
    f"({environments.env_dir(model_id)}).\n\nOpen Settings > Manage "
    "the STT and install this model there."
)
Distinguishing "not installed" from "it broke" is a product decision. Both are exceptions, but the first is a normal state of a fresh machine and the second is a bug. The dialog handles them differently: one offers to open Settings, the other shows the cause and an exit code. Collapsing them into one message would make the ordinary case look like a failure.

85.6 GPU Is a Driver, Not a Toolkit

A GPU run of any model here needs exactly one thing the user must supply: an NVIDIA driver. The CUDA build of PyTorch is installed into the model's own environment, so a transcription never waits for the optional sherpa-onnx GPU runtime used by the ONNX speech engines — the two features are independent from the user's point of view even though they share a card.

Whisper is the exception that proves the rule, and its fix is the reason cuda_packages exists. Its CTranslate2 back-end dynamically loads cublas64_12.dll, which faster-whisper does not depend on. Without it the run does not crash — it quietly uses the CPU:

"cuda_packages": ["nvidia-cublas-cu12"],   # the wheel ships cuDNN itself

Because a silent fallback is worse than a loud failure, Manage the STT checks for the wheel and, when an existing environment predates it, names it and turns Install selected model into a repair.

85.7 Exercises

  1. Add a second worker protocol (say, JSON-lines on stdin) behind a flag. Which parts of _run_worker stay the same?
  2. Measure how long a directory-read probe takes for an environment with 300 distributions, and compare it with pip list.
  3. A model needs protobuf>=5 and another needs protobuf<4. Write the two catalog entries and show that neither install can disturb the other.

Key Takeaways

  • Isolation costs disk, and buys the property that two models can never break each other; for conflicting stacks that is a good trade.
  • Probe site-packages directly when a UI needs to know what is installed — never shell out to pip on a paint event.
  • Install GPU packages first, and only on a machine that has the hardware.
  • A one-shot worker subprocess with file-based results is easier to cancel and reason about than a long-lived server.
  • Filter stderr down to the real cause, keep the exit code, and say plainly when the reason is "not installed yet".
