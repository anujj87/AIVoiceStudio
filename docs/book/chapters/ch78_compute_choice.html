Chapter 78

Compute Choice: CPU, GPU and How Much of Each

Learning Objectives

  • Split “how much of the machine may a run use?” from “which device does it run on?”
  • Compute a CPU thread count that stays inside an 80–95 % band, on any core count
  • Use the whole of whatever NVIDIA card is present, without model or VRAM checks
  • Offer the choice per category in the UI, remembering each category’s answer
  • Apply the decision inside a worker process with PyTorch’s own knobs

78.1 Two Questions Users Actually Ask

“Which processor should this use?” hides two requirements that look similar and must be implemented very differently:

RequirementQuestion it answersWhere it lives
Device choiceGPU or CPU for this run?compute.resolve_compute, voicelab.resolve_device
BudgetHow much of that device may the run consume?compute.cpu_threads, worker _maximize_cuda / _limit_cpu

The requirements as stated by the user were concrete:

  • On GPU: use the maximum compute available on whatever NVIDIA card is installed — no model whitelist, no VRAM minimum.
  • On CPU: use between 80 % and 95 % of the available CPU.

78.2 Detecting the GPU Once, Cheaply

_nvidia_cache: bool | None = None


def has_nvidia_gpu(force: bool = False) -> bool:
    global _nvidia_cache
    if _nvidia_cache is not None and not force:
        return _nvidia_cache
    try:
        flags = 0
        if sys.platform == "win32":
            flags = getattr(subprocess, "CREATE_NO_WINDOW", 0)
        result = subprocess.run(
            ["nvidia-smi", "--query-gpu=name", "--format=csv,noheader"],
            capture_output=True, text=True, timeout=10, creationflags=flags,
        )
        found = result.returncode == 0 and bool(result.stdout.strip())
    except Exception:
        found = False
    _nvidia_cache = found
    return found

Explain Line by Line Code Description (Block 1)

  1. Line 1: a module-level cache
    A tri-state (None = never asked). This matters: “not yet asked” and “asked, answer is no” are different, and collapsing them would re-run the driver query on every combo box the user opens.
  2. Lines 4–6: the optional force
    A “Re-detect” button and the tests need today’s hardware, not the answer cached when the process started. Caching plus an explicit escape hatch is the polite version of a global.
  3. Lines 8–11: CREATE_NO_WINDOW
    A Windows detail that matters in a GUI app: without this flag, running nvidia-smi flashes a console window over the user’s screen. getattr with a default keeps the same code working on Linux and macOS.
  4. Lines 12–16: the query
    Driver-only detection: nvidia-smi exists wherever an NVIDIA driver is installed, so this asks “is there a usable GPU?” without importing PyTorch or downloading a runtime. The query asks only for the name, because that is the smallest answer that can prove the driver responded.
  5. Line 17: the except Exception branch
    A missing executable, a non-zero exit, a timeout — every one of them means “no GPU”, never a crash. Detection is best-effort by definition.

The option “GPU” and the ability to run on the GPU are separate concerns, and the docstring in compute.py is explicit about it:

def _has_cuda(force: bool = False) -> bool:
    if not runtime.is_installed():
        return False
    return has_nvidia_gpu(force)


def detect(force: bool = False) -> Dict[str, bool]:
    cache = getattr(detect, "_cache", None)
    if cache is not None and not force:
        return cache
    result = {
        COMPUTE_CPU: True,
        COMPUTE_CUDA: _has_cuda(force),
        COMPUTE_DML: _has_npu(),
    }
    detect._cache = result
    return result

Explain Line by Line Code Description (Block 2)

  1. Lines 1–4: _has_cuda
    Two conditions, one per cause of failure. The ONNX engines need the optional GPU runtime and a driver; the runtime is an explicit download because it is roughly 1.8 GB and most users never need it. The pip-installed Voice Lab engines bypass this path entirely — they bring their own PyTorch, so for them a driver is enough (see provider_for_preview in 78.5).
  2. Line 8: a cache stored on the function object
    detect._cache is a small, readable alternative to decorating with functools.lru_cache — it can be cleared for tests, and it is obviously per-process state.
  3. Lines 10–15: the result dictionary
    CPU is hard-coded True: the bundled runtime always exists. DirectML stays False because no DirectML/NPU runtime exists for sherpa-onnx — the option is deliberately not offered rather than offered and broken.
  4. Why not import onnxruntime to ask?
    Because sherpa-onnx ships its own runtime and loading a second onnxruntime into one process corrupts the graph loader (two DLLs with the same module name). Detection therefore reads files and drivers, never imports.

78.3 The CPU Band: 80–95 % Done Right

“Use 80–95 % of the CPU” is easy to say and surprisingly fiddly to implement, because thread counts are integers and small machines break naive arithmetic. The whole rule is four useful lines:

CPU_THREAD_MIN_RATIO = 0.80
CPU_THREAD_MAX_RATIO = 0.95


def cpu_threads(total: Optional[int] = None) -> int:
    try:
        cpus = int(total if total is not None else (os.cpu_count() or 1))
    except (TypeError, ValueError):
        cpus = 1
    if cpus <= 1:
        return 1
    low = max(1, int(math.ceil(cpus * CPU_THREAD_MIN_RATIO)))
    high = max(1, int(math.floor(cpus * CPU_THREAD_MAX_RATIO)))
    if high < low:
        return max(1, cpus - 1)
    return max(1, min(high, cpus))

Explain Line by Line Code Description (Block 3)

  1. Lines 1–2: the band as named constants
    Two floats with names, not magic numbers inside the function. They are also importable, so documentation and tests quote the same rule the code implements.
  2. Lines 6–9: reading the core count
    total exists so tests can ask “what would you do on a 3-core machine?” without owning one. os.cpu_count() or 1 handles the documented case where Python cannot report a count. The int() conversion inside a try guards against a caller passing a string.
  3. Lines 10–11: the single-core case
    A one-core machine gets its one core. No rule about leaving room can be satisfied when there is only one resource, so the honest answer is “all of it”.
  4. Lines 12–13: the band, using ceil and floor
    The lower bound rounds up (80 % of 10 cores is 8.0 → 8; 80 % of 6 is 4.8 → 5) and the upper bound rounds down (95 % of 10 is 9.5 → 9). Rounding inwards is what keeps the result inside the promised band instead of just outside it.
  5. Lines 14–15: the small-machine escape
    On two or three cores the band is empty (on 2 cores: low = 2, high = 1). Returning cpus - 1 keeps the intent of the rule — leave a little headroom so the desktop, the Recording window and the audio writer stay responsive — instead of returning an impossible number or crashing.
  6. Line 16: the chosen value
    The top of the band, clamped to cpus. The requirement was “as much CPU as possible within the rule”, so the maximum of the band is deliberate: 15 of 16 threads, 30 of 32. The single reserved core is what keeps the UI responsive during a long recording.

Worked examples — the same function, six machines:

Watching that table is the fastest way to understand the high < low branch: on 4 cores, 80 % is 3.2 (→ 4) and 95 % is 3.8 (→ 3), so no integer satisfies the literal rule. The code chooses the closest honest behaviour — one core free — instead of pretending.

78.4 The GPU Rule: Any NVIDIA Card, All of It

def cuda_device_index() -> int:
    return 0


def gpu_summary() -> str:
    if not has_nvidia_gpu():
        return ""
    result = subprocess.run(
        ["nvidia-smi", "--query-gpu=name,memory.total", "--format=csv,noheader"],
        capture_output=True, text=True, timeout=10, creationflags=flags,
    )
    first = (result.stdout or "").strip().splitlines()
    if result.returncode == 0 and first:
        return first[0].strip()
    return ""

Explain Line by Line Code Description (Block 4)

  1. Lines 1–3: cuda_device_index
    Returns 0, with the reasoning written in the docstring: an engine process drives one device, and the driver exposes the cards in a fixed order, so “the first” is the whole story. There is deliberately no VRAM threshold and no model list — any CUDA-capable NVIDIA card is accepted, which is exactly the requirement.
  2. Lines 6–7: the “no GPU” answer
    Empty string instead of an exception: this value is shown in a status label, and “no GPU” is a normal state, not an error.
  3. Lines 8–12: the richer query
    Name and total memory, purely for display. Users like knowing which card the application will use, and the memory number makes a slow run easier to explain than a bare model name.
  4. Lines 13–16: the first line only
    Multi-GPU machines list several cards. The application uses the first, so it displays the first — reporting a second card would describe a device the run does not touch.
def _maximize_cuda(torch):
    try:
        if not torch.cuda.is_available():
            return False
        torch.cuda.set_device(0)
    except Exception:
        return False
    try:
        torch.backends.cudnn.benchmark = True
        torch.backends.cuda.matmul.allow_tf32 = True
        torch.backends.cudnn.allow_tf32 = True
    except Exception:
        pass
    try:
        torch.set_float32_matmul_precision("high")
    except Exception:
        pass
    try:
        torch.set_grad_enabled(False)
    except Exception:
        pass
    return True

Explain Line by Line Code Description (Block 5)

  1. Lines 2–6: the availability gate
    torch.cuda.is_available() is the engine’s own truth: a driver can exist while a CUDA build of PyTorch cannot use it. set_device(0) pins the process to the first card, matching cuda_device_index().
  2. Lines 7–12: the fast kernels
    cudnn.benchmark lets cuDNN pick the fastest convolution algorithm for the shapes it sees — ideal here, because recording a book reuses the same shapes thousands of times. TensorFloat-32 enables the tensor-core paths on float32 maths, which is a large speed-up for inference on modern NVIDIA hardware.
  3. Lines 13–16: precision policy
    "high" float32 matmul precision means “use the fast tensor-core path where it is numerically safe”. It is the documented, portable way to ask for that, rather than relying on individual backend flags.
  4. Lines 17–20: inference mode
    These engines only ever run forward passes, so autograd’s bookkeeping is pure overhead — memory and time spent recording gradient information nobody reads. Turning it off system-wide inside a dedicated worker process is safe precisely because that process does nothing else.
  5. Every block is guarded separately
    Each optimisation is wrapped in its own try/except. An older PyTorch may not have set_float32_matmul_precision, and one unavailable knob must not cost the user the other three.
def _limit_cpu(torch, threads):
    if not threads:
        return False
    try:
        value = max(1, int(threads))
    except (TypeError, ValueError):
        return False
    try:
        torch.set_num_threads(value)
    except Exception:
        pass
    try:
        torch.set_num_interop_threads(max(1, value // 2))
    except Exception:
        # Raised once parallel work has started; the per-op thread pool set
        # above is the one that decides how much CPU inference uses.
        pass
    return True


def _apply_compute_settings(device, threads=None):
    try:
        import torch
    except Exception:
        return
    if str(device).lower() == "cuda":
        _maximize_cuda(torch)
    else:
        _limit_cpu(torch, threads)

Explain Line by Line Code Description (Block 6)

  1. Lines 1–7: validating the number
    threads arrives over a JSON pipe from another process, so it is treated as untrusted input: a missing or unparsable value simply means “no limit specified”. max(1, int(...)) prevents the write of a zero or negative thread count, which PyTorch rejects.
  2. Lines 8–11: set_num_threads
    The knob that actually decides how much CPU inference uses: the size of the intra-op thread pool. This is where the 80–95 % band becomes reality.
  3. Lines 12–17: set_num_interop_threads
    The pool used when different operations run in parallel — half the intra-op size, because inter-op parallelism is coarser and gains less from many threads. PyTorch raises if this is called after parallel work has begun; the comment records that the call above is the one that matters, so the exception is intentionally swallowed.
  4. Lines 19–24: one entry point
    The worker calls _apply_compute_settings(device, threads) once when it loads an engine, and the branch is deliberately a plain if/else: a GPU run maximises the card, everything else limits the CPU. A try around the import means a CPU-only environment can never fail because PyTorch is absent.

78.5 The Combo Box Next to Every Preview Button

The compute choice is offered where a voice is actually heard: next to each category’s Preview button. The widget code is small because every decision was written as a pure function first.

SETTINGS_PREFIX = "preview_compute"


def choices() -> List[Tuple[str, str]]:
    options = [("cpu", "CPU")]
    if compute.has_nvidia_gpu():
        options.append(("cuda", "GPU (CUDA)"))
    if len(options) > 1:
        options.append(("auto", "Auto (GPU when possible)"))
    return options


def settings_key(category: str) -> str:
    return f"{SETTINGS_PREFIX}.{category}"


def saved_choice(settings, category: str) -> str:
    return _stored_choice(settings, category) or "cpu"


def provider_for_preview(choice: str, engine_id: Optional[str] = None) -> str:
    if engine_id:
        from ..voicelab import engines as voice_lab
        if voice_lab.is_engine(engine_id):
            from ..voicelab import resolve_device
            return resolve_device(choice)
    return compute.provider_for(compute.resolve_compute(choice))

Explain line by line code description (Block 7)

  1. Line 1: SETTINGS_PREFIX = "preview_compute"
    The key names and the constant have to agree forever, so the constant is the only place the string is written. The module docstring records why it is not compute.preview: compute is a plain string setting, so nesting under it makes Settings.set fail and silently drops every category’s choice.
  2. Lines 4–11: choices()
    CPU is always offered; GPU appears only when a driver is detected; Auto appears only when there is something to choose between (with a single option, “Auto” is a synonym for “CPU” and would only confuse). len(options) > 1 is checked before appending, so the logic reads top to bottom.
  3. Lines 14–15: settings_key
    One category, one key — “preview_compute.voicelab”, “preview_compute.omnivoice”. Per-category memory is what makes “GPU here, CPU there” possible.
  4. Lines 18–19: saved_choice
    Returns the stored value or the default "cpu". Only values that are still valid on this machine are returned (see _stored_choice), so a settings file copied from a GPU machine to a CPU-only laptop does not select an option the combo cannot show.
  5. Lines 22–28: provider_for_preview
    The interesting branch. A Voice Lab engine resolves the device through its own PyTorch (resolve_device — no downloaded runtime needed), while every ONNX engine goes through compute.resolve_compute and needs the optional GPU runtime. That single difference is why the code asks “is this a Voice Lab engine?” rather than mapping the value directly.
def make_compute_row(parent, settings, category, default="cpu"):
    label = wx.StaticText(parent, label="Compute:")
    combo = wx.ComboBox(parent, style=wx.CB_READONLY, name="Compute")
    set_accessible_name(combo, "Compute")
    combo.SetToolTip(
        "Which back-end the Preview uses: CPU, GPU (CUDA, when an NVIDIA GPU "
        "with a driver is detected) or Auto."
    )
    options = choices()
    for value, text in options:
        combo.Append(text, value)
    available = {value for value, _text in options}
    stored = _stored_choice(settings, category)
    current = stored or (default if default in available else "cpu")
    if current not in available:
        current = "cpu"
    for index in range(combo.GetCount()):
        if combo.GetClientData(index) == current:
            combo.SetSelection(index)
            break
    else:
        combo.SetSelection(0)

    def _persist(_evt):
        if settings is None:
            return
        try:
            settings.set(settings_key(category), _combo_value(combo))
        except Exception:
            pass

    combo.Bind(wx.EVT_COMBOBOX, _persist)
    return label, combo

Explain Line by Line Code Description (Block 8)

  1. Lines 2–4: the label and combo
    CB_READONLY prevents typing a value the code cannot resolve — a read-only combo is a promise that every reachable value is valid. Naming the control (“Compute”) is what makes NVDA announce it as something other than “combo box”.
  2. Lines 5–8: the tooltip
    A tooltip is not decoration here: it is the only place the user learns that ONNX engines need the GPU runtime downloaded from Settings, which is the difference between “GPU does not work” and “I need to install the runtime”.
  3. Lines 9–11: appending values with client data
    combo.Append(text, value) stores machine-readable data behind the human label, so no code ever compares translated display text. Renaming a label then cannot break the logic.
  4. Lines 12–14: resolving the selection
    Stored choice first, then the caller’s default if it is actually available, then CPU. The if current not in available re-check closes the last hole — an engine that requires the GPU passes default="cuda", and on a machine without a GPU it degrades to CPU rather than showing an impossible selection.
  5. Lines 15–20: selecting it
    The loop searches by client data; the else clause of the for runs when nothing matched and selects the first item — a construct many Python programmers forget exists, and one that removes a “did I find it?” flag variable.
  6. Lines 22–30: remembering the choice
    Persisted on EVT_COMBOBOX, immediately. A preference that is forgotten until “OK” is a preference that is lost when the dialog is cancelled; and settings failures are swallowed because a preference must never raise inside an event handler.
Return a (label, combo) tuple rather than a panel: the caller decides layout, and every settings category can place the row wherever its Preview button already is.

78.6 Mini Project: Watch the Band Decide

from ai_voice_studio import compute

print("this machine :", compute.cpu_threads(), "threads of",
      __import__("os").cpu_count())
for cores in (1, 2, 3, 4, 6, 8, 12, 16, 24, 32, 64):
    threads = compute.cpu_threads(cores)
    print(f"{cores:>3} cores -> {threads:>3} threads "
          f"({threads / cores:.0%})")

print("GPU         :", compute.has_nvidia_gpu())
print("card        :", compute.gpu_summary() or "(none detected)")

  2. On a machine with an NVIDIA GPU, record a paragraph twice — once with the combo on CPU and once on GPU — and compare the wall-clock times. Which part of the difference comes from _maximize_cuda rather than raw hardware?
  3. Write a test for cpu_threads that asserts the result is inside the band whenever the band is non-empty, and equals cores - 1 when it is empty. Run it for every core count from 1 to 64.
  4. Explain why provider_for_preview treats Voice Lab engines differently from ONNX engines, and what would break if it did not.

78.7 Key Takeaways

  • Separate device choice from resource budget — they have different APIs and different failure modes
  • Detect hardware with the driver (nvidia-smi), never by importing a framework
  • Round inwards to stay inside a percentage band, and define behaviour for machines where the band is empty
  • Accept any CUDA-capable NVIDIA card: no model list, no VRAM minimum, use the whole card
  • Apply the CPU share in the worker with set_num_threads, and let the application decide the number
  • Offer the choice per category and store it under a namespaced key that cannot collide with an existing setting
  • Guard every optional backend flag separately, so one missing knob costs only itself
