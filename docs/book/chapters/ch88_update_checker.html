Chapter 88

Checking for Updates: A Pure Decision and a Network Side Effect

Learning Objectives

  • Split a network feature into a pure decision function and an I/O function
  • Compare version strings that carry a v prefix or a suffix
  • Pick the installer for the running architecture from a release's assets
  • Design a check that stays quiet unless it has something to say
  • Reuse an existing resumable download instead of writing a second one
  • Publish the same installer to winget without changing the code

88.1 Two Ways In, One Truth

There are two entry points and they behave differently on purpose:

  • A quiet automatic check at start-up, at most once a day (settings["updates"]["auto_check"]). It speaks only when a newer version exists and the user has not muted that exact version. A failure is silent — an offline laptop must not see an error box on every launch.
  • Help → Check for updates (Alt+D), which always answers: a newer version with its release notes, “you already have the newest version”, or a plain reason when GitHub cannot be reached.

The single source of truth is the repository's latest release:

LATEST_RELEASE_API = "https://api.github.com/repos/anujj87/AIVoiceStudio/releases/latest"
The user asked, so the user is told. A background check that reports a network failure trains people to ignore it; a menu item that leaves the question unanswered is broken. Same feature, two contracts — and the difference lives in the dialog layer, not in the networking code.

88.2 The Decision Is a Pure Function

The interesting part of an update check is not the HTTP request; it is the decision. So the decision takes the JSON payload as an argument and touches nothing:

def evaluate_release(payload: dict, current: str = APP_VERSION) -> UpdateCheck:
    """Decide from a GitHub ``releases/latest`` payload whether to offer an update.

    A draft release is ignored; a prerelease is offered like any other
    release because this project publishes its installers exactly that way.
    """
    if not isinstance(payload, dict):
        return UpdateCheck(current=current, error="Unexpected release data from GitHub.")
    if payload.get("draft"):
        return UpdateCheck(current=current, latest=None, available=False)
    ...
    return UpdateCheck(current=current, latest=release,
                       available=is_newer(version, current))

That shape is what makes the version rules testable without a network: the test suite feeds hand-written payloads to evaluate_release() and checks the decision, including the awkward cases — a draft release, a release whose tag has no digits, a release that is older than the running build.

88.3 Comparing Versions Without a Date Library

A release tag may be v2026.3.7, 2026.3.7, or 2026.3.7-beta. Rather than parse a version scheme, the project takes the leading numeric run(s) and pads them:

def parse_version(text: str) -> tuple:
    """Turn ``"v2026.3.7"`` / ``"2026.3.7-beta"`` into ``(2026, 3, 7)``.

    Only the leading numeric run(s) are used, so a release tag may carry a
    ``v`` prefix or a suffix without breaking the comparison.  A tag with no
    digits at all yields ``()`` and simply never compares as newer.
    """
    numbers: list[int] = []
    current = ""
    for char in str(text or ""):
        if char.isdigit():
            current += char
        elif char == "." and current:
            numbers.append(int(current))
            current = ""
        elif current:
            break
    if current:
        numbers.append(int(current))
    return tuple(numbers)


def is_newer(remote: str, local: str = APP_VERSION) -> bool:
    """True when ``remote`` names a strictly newer version than ``local``."""
    remote_parts = parse_version(remote)
    if not remote_parts:
        return False
    return _pad(remote_parts) > _pad(parse_version(local))

Padding matters: without it (2026, 3) would compare greater than (2026, 3, 7) on a tuple of different lengths, and a truncated tag would be read as a newer release. The rule is deliberately conservative — a tag with no digits never counts as newer, so a mistyped release name can never downgrade or upgrade anybody by accident.

88.4 Picking the Installer for This Machine

A release carries several assets, and the right one depends on the running interpreter's width:

ASSET_MARKERS = {"x64": "setup-x64", "x86": "setup-x86"}

class ReleaseInfo:
    def asset_for_arch(self, arch: str) -> Optional[ReleaseAsset]:
        marker = ASSET_MARKERS.get(arch, ASSET_MARKERS["x64"])
        for asset in self.assets:
            if marker in asset.name.lower():
                return asset
        return None

def current_arch() -> str:
    """``"x64"`` or ``"x86"`` for the *running* interpreter."""
    return "x64" if struct.calcsize("P") * 8 == 64 else "x86"

Using the interpreter's own pointer size, rather than the operating system's, is the honest answer: it is the binary that is running and therefore the binary that must be replaced. The same architecture choice drives the download in tools/make_winget.py and the installer build.

88.5 Errors That Are Answers

The check never raises to its caller. Failures become a value:

def check_for_update(current: str = APP_VERSION, timeout: int = DOWNLOAD_TIMEOUT) -> UpdateCheck:
    """Look for a newer release. Never raises: a failure is reported in the result."""
    try:
        payload = fetch_latest_release(timeout=timeout)
    except UpdateError as exc:
        return UpdateCheck(current=current, error=str(exc))
    except Exception as exc:  # noqa: BLE001 - a check must never break the app
        log.debug("Update check failed", exc_info=True)
        return UpdateCheck(current=current, error=f"Could not check for updates: {exc}")
    return evaluate_release(payload, current)

This is the same discipline Chapter 84 used for a missing model: make the ordinary unhappy path a state, not an exception. An exception that escapes a start-up check is a crash before the user has done anything; an UpdateCheck with an error string is a sentence in a dialog. Note also the broad except Exception with a comment saying why — the one place where catching everything is correct is the place whose whole job is to not break the application.

88.6 Downloading Without Writing a Downloader

The application already has a resumable, cancellable transfer for model files: Range requests and .part files, built in Chapter 49. The update reuses it rather than growing a second one, which means an interrupted 2 GB installer download resumes exactly like an interrupted voice download.

def launch_installer(path: str, silent: bool = False) -> None:
    """Start the downloaded installer (and let go of it).

    ``silent`` runs Inno Setup with ``/SILENT`` (a progress window, no
    questions); it is the same switch winget uses.
    """
    args = [path]
    if silent:
        args += ["/SILENT", "/SUPPRESSMSGBOXES", "/NORESTART"]
    if os.name == "nt" and not silent:
        os.startfile(path)      # a normal double-click: the familiar wizard
    else:
        subprocess.Popen(args)
The installer is per-user by default. Because PrivilegesRequired=lowest and PrivilegesRequiredOverridesAllowed=dialog are set, an update started from inside the application needs no administrator rights: Inno takes the recommended choice when it is not answered. A user who originally installed for all users is found by the same AppId and updated in place.

88.7 The Same Installer, in winget

winget is a second door to the same room, not a second build. The repository ships three generated manifests under winget/manifests/a/AnujSharma/AIVoiceStudio/<version>/:

FileHolds
...AIVoiceStudio.yamlthe package identity and its version
...installer.yamlthe versioned download URL, the SHA256 of those exact bytes, the silent switches, the installer type
...locale.en-US.yamlthe display name, publisher and description
 
# tools/make_winget.py   - the manifests are derived, not typed
# tools/winget_validate.py - checked against winget's own rules
# tests/test_winget.py    - runs that validator inside the suite

The generation pipeline is the point. The manifests take the version from constants.APP_VERSION, the tag from the release, and the SHA256 from the built installer — so the hash describes bytes that actually exist. winget_validate.py checks the result against the rules the Windows Package Manager will apply, and the test suite runs it, so a manifest that would be rejected fails the build instead of the PR.

An asset's bytes are permanent. Once a version is in winget, its installing file's hash is pinned forever in a manifest that lives in another repository. Re-uploading rebuilt bytes over the same release, or deleting the release, breaks that pinned version for everyone who has not installed it yet. The safe rule is the one the build follows: build once, generate the manifests from those bytes, never touch that release again, and publish the next version as a new release. The project's own tests cross-check the version across README.md, the manifests and the installer for the same reason.

88.8 Exercises

  1. Add a "skip this version" that is remembered per version (not a single global mute). Which function changes, and what does the settings block look like?
  2. The release notes are GitHub-flavoured Markdown. Write the smallest renderer that shows them readably in the dialog, or argue for a plain-text rendering.
  3. Make the update check use a conditional request (If-None-Match) so a daily check costs nothing when nothing changed.

Key Takeaways

  • Put the decision in a pure function and the network in a thin one; then the rules are testable without a connection.
  • Parse versions conservatively: a tag that is not a version is never newer.
  • Answer the user when they ask, stay silent when they did not.
  • Reuse the download transfer you already have; a second implementation is a second set of bugs.
  • Generate packaging manifests from the artifact, validate them in the test suite, and never rewrite the bytes a released manifest points at.
