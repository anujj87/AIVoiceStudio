Chapter 90

A Catalog of Describers, and One Environment per Model

Learning Objectives

  • Describe a model catalogue that carries licences, sizes and costs
  • Separate a model's environment from a variant's checkpoint
  • Build one Python environment per model and repair it when it is incomplete
  • Explain why a CUDA-only package turns Install into Repair
  • See why a model that runs its own modelling code decides part of its own environment
  • Load a checkpoint larger than the graphics card without spilling to disk

90.1 The Catalogue Is Data

describe/catalog.py is a table, not code: each model declares its id, name, licence, notes, whether it needs trust_remote_code, whether it can report timestamps and the pip packages its environment needs. Each variant adds one checkpoint:

_variant(
    "4b", "Qwen3-VL-4B",
    size_gb=8.0, vram_gb=7.0, fit="gpu", cpu_ok=True,
    gpu_cost=40.0, cpu_cost=180.0,
    hf="Qwen/Qwen3-VL-4B-Instruct",
),

size_gb is the download; vram_gb is what the checkpoint wants in video memory; gpu_cost and cpu_cost are seconds of compute per minute of video at the catalogue's reference frame rate, and the estimator scales them by the frame rate the user chose. Everything the Settings table, the wizard's state labels and the run's decisions need comes from this one description, which is why adding a model is a data change and not a code change.

90.2 Environment and Checkpoint Are Two Things

The most confusable thing about this feature is that installing a model and downloading a variant are different operations with different lifetimes:

Model environmentVariant checkpoint
What it isa Python virtualenv with PyTorch, transformers and the model's own packages the weights of one size of that model
Shared byevery variant of the model nothing — it belongs to one variant
Wheredescribe_envs\<model id> the Hugging Face cache
Removed byRemove model environment Remove variant download
Why this matters in the UI. An earlier build of that screen looked at the model, saw an environment, and treated the whole model as installed — so after downloading Qwen3-VL 4B every other Qwen3-VL variant appeared to be undownloadable. The panel now renders one Install/Repair button for the environment and one Download/Remove button per variant, with a Status column, and engine.variant_state_label() answers the question a row is really asking. 
def variant_state_label(model_id: str, variant: str) -> str:
    variant = variant or catalog.default_variant(model_id)
    if not catalog.hf_model(model_id, variant):
        return "No download for this choice"
    if not environments.is_installed(model_id):
        return "Install the model first"
    if variant_downloaded(model_id, variant):
        return "Downloaded"
    size = catalog.variant_size_gb(model_id, variant)
    if weights.is_partly_downloaded(variant_repo(model_id, variant)):
        return (f"Partly downloaded - about {size:.1f} GB in all; download it "
                "again to continue where it stopped")
    return f"Not downloaded (about {size:.1f} GB)"

"Partly downloaded" is a state of its own because it is what a cancelled or failed fetch leaves behind: the files are on disk, the checkpoint cannot be loaded, and the download that would finish it is still available. Calling that "not downloaded" sends the user looking for gigabytes that are already there.

90.3 Building the Environment

describe/environments.py has the same shape as the speech-to-text one: a plan of pip packages, a virtualenv created under %APPDATA%\AIVoiceStudio\describe_envs, and a worker_script()/runtime() pair the engine uses to start the worker. Two details carry weight:

  • CUDA-only packages. A package needed only for a GPU run is declared separately and installed on a machine with an NVIDIA card. Whisper needed cuBLAS this way in the speech-to-text half; here it is bitsandbytes, the 4-bit quantiser. When such a package is missing from an environment that already exists, Install becomes Repair model environment and names what is missing.
  • Declared packages, not just the back-end. environments.is_installed() proves the back-end imports, which is a narrower question than “is this environment complete”. missing_packages() asks the wider one - every package the catalogue declares for that model, against the environment's own site-packages - and the same Repair rule covers it. That is what makes a requirement discovered late (90.5) repairable in an environment that already exists, rather than only in a new one.
  • A missing runtime, said out loud. engine.gpu_runtime_missing() reports the CUDA wheel an environment lacks, so the Settings panel can explain a GPU run that would otherwise fall back to the CPU silently.

90.4 A Model Bigger Than the Card

The hardest failure this feature produced was not an error message. It was exit code 0xC0000005, an access violation, and a dialog that blamed a warning about Windows symlinks printed three lines above the crash. The cause was device_map="auto", which offloads part of an oversized model to the disk. A model on the disk is a set of meta tensors, and the forward pass over them kills the process.

The loader therefore places the model explicitly — never on the disk — and asks for 4 bits when the weights cannot fit:

card = _gpu_total_gib(torch_module)
size = float(request.get("model_size_gb") or 0.0)
budget = max(1.0, card - _GPU_HEADROOM_GIB)
too_big = bool(size) and size > budget
quantized, why = _quantized_config(torch_module)

attempts = []
if too_big and quantized is not None:
    attempts.append((quantized, (
        f"This model is about {size:.1f} GB of weights and this card holds "
        f"{card:.1f} GB, so it was loaded in 4-bit."
    )))
else:
    attempts.append((None, ""))
    if quantized is not None:
        attempts.append((quantized, (
            "The model did not fit this card at full precision, so it was "
            "loaded in 4-bit."
        )))

The placement handed to from_pretrained is {"": 0} — everything on card 0 — and only a model that can be run neither way is refused, with its own reason. Gemma 3 12B is about 24 GB of weights and runs on a 12 GB card in 4-bit form (roughly a quarter of that) with room to generate; the only cost is that the environment must have bitsandbytes, which is exactly what Repair is for.

Refuse, do not crash. A process that dies prints nothing, so its exit code is the only fact available. engine._crash_note() turns 0xC0000005 into "the model's process stopped (exit code 3221225477: an access violation) before it produced a description. The usual cause is that the chosen model did not fit in this machine's video memory and system memory; a smaller variant … runs instead."

90.5 When the Model's Own Code Chooses the Environment

One entry in the catalogue runs the checkpoint's own Python: MiniCPM-o 2.6 ships trust_remote_code, so transformers downloads its modelling, processing and utility files and executes them. Those files import libraries no other describing model needs, and the first real failure this caused arrived as a sentence from the library, not from us:

Could not load the model: This modeling file requires the following packages
that were not found in your environment: torchaudio. Run `pip install torchaudio`

That message is accurate and useless at once: the user of an installed application has no environment to pip install into, and the instruction names the first missing package rather than the last. Two things follow from it.

There is a second half to that fix, and it is the half the message asks for: Repair has to be reachable. An environment built before those two packages were declared still reports itself installed - it has transformers, the back-end the probe looks for - so the panel would offer only Remove model environment, and the way back to a working model would be a fresh multi-gigabyte PyTorch install. missing_packages() compares the catalogue's declared packages against that environment's own site-packages, and a non-empty answer turns Install into Repair and names the packages in the status line.

A remote-code model's requirements belong in its catalogue entry. transformers refuses to load processing_minicpmo.py without torchaudio, and modeling_minicpmo.py pulls utils.py, which imports librosa - so both are declared packages, and the Install/Repair button becomes the answer to the library's own suggestion. One of them carries the other: librosa requires soxr, and from transformers 5 on, transformers.audio_utils imports soxr whenever librosa is importable. Half an install (librosa without soxr) breaks import transformers itself, which is why the pair must be installed together and why declaring librosa is the whole fix.

A model written for one library release needs that release. MiniCPM-o 2.6's code imports WHISPER_ATTENTION_CLASSES from transformers.models.whisper, and that name is a boundary rather than a detail: 4.52.0 still defines it and 4.53.0 removed it, so the entry pins transformers<4.53 and lets pip resolve the newest member of the series. Two failures are on record for wanting the boundary - 5.19.0 and 4.57.6 both fail on that one import line, which is why the pin could not simply be “below five”.

The exact release the model card names - 4.44.2, which is also what the checkpoint's own config.json records as transformers_version - is deliberately not what the pin asks for: 4.44.2 requires tokenizers<0.20, whose newest Windows wheel is cp312, so an environment on Python 3.13 (and PyTorch 2.11) cannot have it without a Rust toolchain to build the wheel. Pinning to the newest release that still defines the name is what satisfies both constraints - the same shape as the NeMo speech-to-text pin in Chapter 84.

The pin is only safe because of 90.2. A package pin is dangerous in a shared environment and free in a private one. Because every describing model has a virtualenv of its own, a transformers<4.53 entry cannot reach a TTS engine, a speech-to-text model or another describer - and the test suite asserts that no other catalogue entry carries the pin, so a copy-paste cannot quietly spread it. 
_REMOTE_CODE_TRANSFORMERS = "transformers<4.53"

"pip_packages": [_REMOTE_CODE_TRANSFORMERS, "torch", "torchvision",
                 "torchaudio", "accelerate", "pillow", "numpy",
                 "librosa", "soundfile"],

torchaudio is one of _CUDA_PACKAGES, so on a machine with an NVIDIA card it is installed from the same PyTorch wheel index as torch and torchvision - a CUDA torch beside a PyPI (CPU-only on Windows) torchaudio is a runtime crash, not a warning. On a machine with no card the whole list installs from PyPI in one step, and the CUDA-only quantiser is left out altogether.

90.6 Exercises

  1. Add a variant to a model in the catalogue, and list every screen that changes without any code being touched.
  2. Why does the estimate scale a variant's cost by the frame rate but not by the number of descriptions?
  3. The quantiser is a CUDA-only package. What should happen on a machine with no NVIDIA card whose system memory is smaller than the checkpoint?
  4. A new trust_remote_code model is added to the catalogue and a run fails on an import inside its modelling file. Where does the fix belong, and what would you check before writing it?

Key Takeaways

  • Catalogue models as data: licences, sizes, devices and costs.
  • An environment and a checkpoint are separate things; keep them separate in the UI and in the vocabulary.
  • Never let a loader spill to the disk. Place explicitly, quantise when it is needed, and refuse with a reason when neither works.
  • A library's "run pip install X" is a bug report about your catalogue when the model runs its own code: declare the package, in the right environment, with the library release the model was written for.
  • Turn an exit code into a sentence: a killed process leaves nothing else.
