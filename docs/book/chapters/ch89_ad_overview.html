Chapter 89

Audio Description: Narrating What Is on Screen

Learning Objectives

  • Say what audio description is, and who it is for
  • Separate the three things a run produces and who each one is for
  • Explain why the source video must never be written to
  • Lay out the package the feature is built from
  • Recognise the two ways a description can be placed in time

89.1 What Audio Description Is

An audio description is the narration a blind or low-vision viewer needs in order to follow a picture: who is on screen, what they are doing, what the text on the wall says, where the camera goes, what has just changed. It is not a transcript (that is the speech to text half of this application) and it is not a subtitle track (that is one of the outputs, not the whole job). It is writing that has to be short, objective and true, and it has to land between the lines of dialogue without covering them.

The accessibility literature is unusually clear about where the difficulty lives. The VideoA11y study collected guidelines from 154 industry standards and found the same complaints repeating: descriptions that are too long, and descriptions that invent detail the describer could not have seen. Both are prompt problems more than model problems, which is why the guideline prompt is a first-class part of this feature and not a user preference — see ai_voice_studio/describe/prompts.py.

Everything here runs on the user's own machine, exactly like the rest of the application: a vision-language model in a Python environment of its own, FFmpeg for frames, and the voices that were already downloaded for recording.

89.2 The Three Outputs

A run writes three files per video into the project folder, and they serve three different people:

FileFor whom
Lecture.txt — or .html, .srt, .vtt, .json A describer or editor who will review and correct the draft; a player that will speak the SRT/VTT at the right moment; a downstream tool that wants the JSON.
Lecture - narration.wav A listener who wants the descriptions as audio, laid at the times they belong to.
Lecture - described.mp4 The viewer. The film itself, with the description in it: the original picture and sound with the description over the pauses, or the picture stopped for every description.

The first two are documents. The third is what makes this an audio description rather than a description of a video: the viewer plays one file and hears both. It is written by describe/job.py through describe/extended.py, which owns both FFmpeg graphs — one that mixes the description over the film's own soundtrack, and one that stops the film for every description.

Never the source. The described film is a new file, named from the source with a - described suffix, and in standard placement the picture stream is copied with -c:v copy rather than re-encoded, so what the viewer sees is bit-for-bit the source video. Nothing this feature does writes to the source file, renames it or moves it.

89.3 Two Ways to Place a Description

A description has to be heard, and it must not be heard over dialogue. There are exactly two ways to arrange that, and the feature offers both as a single choice called Placement:

  • Standard — speak into a pause of the existing soundtrack. The film is unchanged: its length, its picture and its dialogue are all exactly as they were. This is the right default, and its limit is that a film whose dialogue never stops has no room for it.
  • Extended — stop the film. The picture holds on the frame it had reached, the soundtrack goes quiet, the description is spoken, and the film goes on. Nothing is ever talked over, at the price of a longer film — about eleven seconds per description on the voice measured here, and it is the only option that works for wall-to-wall dialogue.

The two are exclusive because they contradict each other: fitting a description into a pause assumes the film keeps playing. Choosing one therefore switches the other's controls off rather than letting a combination that cannot be honoured sit on screen.

89.4 The Package Layout

ai_voice_studio/describe/
    catalog.py        which models exist, their licences, sizes and costs
    environments.py   one Python environment per model
    weights.py        the per-variant checkpoint cache
    worker.py         the standalone script a model's interpreter runs
    engine.py         starting the worker, reading its response
    pipeline.py       chunking, windows, estimates, gap fitting (pure)
    prompts.py        the guideline prompt
    media.py          FFmpeg probes (length, video files)
    narration.py      text to speech for the descriptions
    extended.py       the plan and the FFmpeg graphs for described films
    output.py         the description documents
    job.py            the background job the dialog starts

The split is deliberate. pipeline.py has no wx, no subprocess and no model: it is arithmetic over numbers and lists, so the decisions that matter — how a video is cut up, how long a run will take, where a description may be spoken — are tested exactly. worker.py is the opposite extreme: it is standalone, imports only transformers, torch and PIL, and is started by the interpreter of a model's own environment, which cannot import the application at all.

A worker, not an import. A describing model drags in a whole PyTorch and transformers version, and two models in this catalogue disagree about both. The application never imports a model's back-end: it writes its request as JSON, starts worker.py with that model's python.exe, and reads the descriptions back the same way.

89.5 Exercises

  1. Add a fourth output: a plain-text list of the moments at which the description speaks, for an editor who will re-record it.
  2. Which of the three outputs can be produced without FFmpeg, and which cannot? Justify each answer from the code.
  3. The described film is named … - described.mp4 in both placements. Why is one name enough?

Key Takeaways

  • Audio description serves a viewer, so a run must end in something watchable — the described film — and not only in documents.
  • The source is read-only; the described film is a new file, and in standard placement its picture is copied rather than re-encoded.
  • Placement is a single choice between speaking into a pause and stopping the film, because a description cannot both wait and not wait.
  • Pure planning in one module and a standalone worker in another is what makes both halves testable.
