Chapter 84

A Second Catalog: Describing Speech-to-Text Models as Data

Learning Objectives

  • Recognise when a second catalog must be plain Python rather than JSON
  • Describe a model with the facts its UI and its runner each need
  • Express a preference (which device to try first) separately from a limit (a device that cannot work)
  • Declare a capability a back-end really has, instead of asking for it and catching the failure
  • Keep a per-variant override so one catalog entry can hold a GPU-only checkpoint and a CPU-friendly one
  • Derive the Settings table from the same data the dialog uses, so the two can never disagree

84.1 Why Speech to Text Needed Its Own Catalog

Chapter 47 built the catalog for the speech engines: a JSON file of ONNX models with download URLs, file names and byte counts. The speech-to-text models are a different kind of thing. They are ordinary Python packages (faster-whisper, transformers, nemo_toolkit, speechbrain) that run in a managed virtual environment, not ONNX graphs with a manifest. There is no download URL to pin and no graph to check a size for — pip resolves the dependencies — so an entry has to describe pip packages, a back-end and a repository id instead.

The consequence is the design decision of this chapter:

The STT catalog is plain Python, not JSON. ai_voice_studio/stt/catalog.py declares its models as a list of dictionaries in code. A JSON catalog needs a schema, a loader, a validator and a way to point at files; for a small list of models whose extra facts (which transformer runner to use, whether the repository needs trust_remote_code) are not expressible as strings anyway, code is the simpler and safer home. The TTS catalog stayed JSON because its data is downloadable, versioned metadata.

Everything else follows the project's usual rule: the catalog is the single description. The Settings table, the transcribe dialog's combos and the worker's request all read from this one module, so a model cannot appear in one place and be missing from another.

84.2 The Shape of an Entry

Every model is a dictionary with the fields its two audiences need. The Settings table (Manage the STT) wants columns; the transcribe dialog and the worker want execution facts.

{
    "id": "whisper_large_v3",
    "name": "Whisper Large V3",
    "license": "MIT",
    "languages_label": "99+",
    "languages": WHISPER_LANGUAGES,
    "fit": "gpu",
    "fit_label": "\u2705 GPU or CPU",
    "notes": "Multilingual and accurate; runs on both a GPU (~10-12 GB "
             "VRAM for Large) and a CPU",
    "variants": _whisper_variants(),
    "default_variant": "large-v3",
    "accuracy_hint": "~10.3% WER (large-v3)",
    "backend": "faster_whisper",
    "pip_packages": ["faster-whisper"],
    # CTranslate2 is a CUDA build on Windows: without the cuBLAS runtime
    # from these wheels every run failed with "Library cublas64_12.dll is
    # not found or cannot be loaded".  The wheel ships cuDNN itself.
    "cuda_packages": ["nvidia-cublas-cu12"],
    "timestamps": True,
    "alt_backends": ["whisper", "transformers"],
    "translation": True,
}

Two fields deserve a closer look, because they were added for a reason.

pip_packages and cuda_packages are separate. The first is what every install needs; the second is what a GPU machine additionally needs. Keeping them apart is what lets a CPU-only computer install a model without downloading a CUDA runtime it can never use — while still fixing the Whisper install that quietly fell back to the CPU because its CTranslate2 back-end could not find cublas64_12.dll.

timestamps is declared, not requested. The transformers library raises

We cannot return_timestamps yet on non-CTC models apart from Whisper!

for every audio language model. So the catalog states which models can really report when each phrase was spoken, and the worker never asks the others for something they cannot give:

{
    "Whisper Large V3":     timestamps=True   # CTC/attention with word times
    "Qwen3-ASR":            timestamps=False  # an audio language model
    "Voxtral":              timestamps=False
    "Granite Speech":       timestamps=False
    "Moonshine":            timestamps=False
}

A model without timings produces one untimed segment, and the SRT/VTT writer still works — it just cannot subtitle precisely, and says so by leaving the timing fields empty rather than inventing numbers.

84.3 Preference Is Not a Limit

A model usually runs on both a CPU and a CUDA GPU; one is simply faster. That is a preference, and the catalog keeps it in fit. A different thing entirely is a model that cannot run without a GPU — Canary-Qwen 2.5B is a speech-language model and Granite Speech 8B is about 17 GB of weights. That is a limit, and it gets its own field:

def gpu_only(model_id: str, variant: str = "") -> bool:
    """Whether this model (or variant) genuinely cannot run without a GPU.

    A speech-language model whose weights alone exceed the RAM of an ordinary
    machine has no usable CPU path, so offering a CPU run would only set the
    user up for a failure.
    """
    entry = model(model_id)
    if entry.get("gpu_only"):
        return True
    return bool(variant) and variant in (entry.get("gpu_only_variants") or [])

The distinction is what makes the Compute combo honest. Instead of asking "does this machine have a GPU?" and hiding everything else, the combo is built from a generous rule that serves the many users who have no card at all:

def device_options(model_id: str, variant: str = "",
                   has_cuda: bool = True) -> List[Tuple[str, str]]:
    """Compute choices the transcribe widget may offer for this model/variant."""
    if gpu_only(model_id, variant):
        if has_cuda:
            return [("cuda", "GPU (CUDA)")]
        return [("cuda", "GPU (CUDA) - no NVIDIA GPU detected, and this model "
                         "cannot run on a CPU")]
    if not has_cuda:
        return [("cpu", "CPU")]          # the only choice that can work
    gpu_option = ("cuda", "GPU (CUDA)")
    cpu_option = ("cpu", "CPU")
    if fit(model_id, variant) == FIT_GPU:
        return [gpu_option, cpu_option]   # the preferred device first
    return [cpu_option, gpu_option]
"Auto" is not offered for transcription. Elsewhere in the application a Compute combo may include Auto because the app can measure and choose sensibly. Here the device is a property of the model and the run is long, so the user is told exactly what will happen and picks it. A choice that would silently fall back when the chosen device cannot work is worse than no choice at all.

84.4 One Entry, Two Devices: the Variant Override

Canary-Qwen ships as two checkpoints under one catalog name. The 2.5B model is GPU-only; the 1B model runs happily on a CPU. Modelling that with two catalog entries would duplicate every fact except the size. Instead the entry carries a per-variant override:

def fit(model_id: str, variant: str = "") -> str:
    """The device this model is *preferred* on ("cpu" or "gpu").

    A variant's ``variant_fit`` overrides the model-level value, because one
    catalog entry can hold both a GPU-only checkpoint and a CPU-friendly one.
    """
    entry = model(model_id)
    overrides = entry.get("variant_fit") or {}
    if variant and variant in overrides:
        return str(overrides[variant])
    return str(entry.get("fit") or FIT_CPU)

Because the device can differ from one variant to the next, the dialog rebuilds the Compute combo when the variant changes. That is the one place where a small amount of UI bookkeeping is unavoidable, and it is cheap: the combo is derived from data, not from special cases.

84.5 Back-ends and Runners

A model names its back-end — the library that will run it — and the back-end id maps to the importable module that proves it is installed:

BACKEND_MODULES: Dict[str, str] = {
    "faster_whisper": "faster_whisper",
    "whisper": "whisper",
    "transformers": "transformers",
    "nemo": "nemo",
    "speechbrain": "speechbrain",
}

But "transformers" is not one interface. The generic ASR pipeline cannot run every architecture: a processor may want a chat prompt plus audio (as Granite Speech does), or the audio-LLM request API (as Qwen3-ASR and Voxtral do). So a model also declares how it must be driven:

RUNNER_PIPELINE = "pipeline"
RUNNER_TRANSCRIPTION_REQUEST = "transcription_request"
RUNNER_CHAT = "chat"

# NeMo mixes plain ASR models (a .nemo checkpoint, ASRModel.from_pretrained)
# with speech-language models (a transformers-style repository that must not
# be sent to the ASR entry point at all).
RUNNER_ASR = "asr"
RUNNER_SALM = "salm"

These names are a contract between two processes: the worker cannot import stt.catalog (it runs on the model environment's own interpreter, where this application is not installed), so both sides spell the runner names the same way and a test pins them together. That is the same technique Chapter 56 used for the synthesis worker, and it is worth repeating: when two processes share a vocabulary, write the vocabulary down once.

84.6 One Table, Derived Not Typed

Settings → Manage the STT shows a table of every model with its licence, its languages, whether it fits the machine and a note. That table is not a second list to maintain — it is projected from the catalog:

def summary_rows() -> List[Tuple[str, str, str, str, str]]:
    """The five columns of the Settings > Manage the STT table."""
    return [
        (m["name"], m["license"], m["languages_label"], m["fit_label"], m["notes"])
        for m in MODELS
    ]

Because the fit column is a stored label rather than a computed one, the entry can be honest about the awkward middle case: a model that runs on both devices but is clearly happier on one. The label reads ✅ GPU or CPU or ✅ CPU or GPU, and the GPU-only checkpoints simply do not use it.

Gated repositories are excluded on purpose. A model whose Hugging Face repository only downloads after signing in and accepting a licence (Cohere Transcribe was one) cannot be installed by a user who has no Hugging Face account, and this application deliberately works without an account. Such a model is not in the catalog at all — no model here needs a token, a login or a licence click-through.

84.7 Exercises

  1. Add a model that reports timings only in its "large" variant. Which fields carry that, and does anything in the dialog need to change?
  2. Give a model a second back-end that is only installed on a GPU machine. Where does that fact belong — pip_packages, cuda_packages, or the environment?
  3. The catalog is plain Python. Write the JSON schema that would be needed to move it to JSON, and list the facts that genuinely cannot be expressed in it.

Key Takeaways

  • A catalog is data, and its form follows its content: JSON for downloadable ONNX metadata, plain Python for pip packages and runner hints.
  • Separate a preference (fit) from a hard limit (gpu_only), and let the UI derive its choices from both.
  • Declare a capability (timestamps) so the runner is never asked for something the back-end will refuse.
  • A per-variant override lets one entry hold a GPU-only checkpoint and a CPU-friendly one without duplicating the entry.
  • Derive the Settings table from the catalog so the two descriptions cannot drift apart.
